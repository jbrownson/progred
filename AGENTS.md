## Cargo

Cargo build scripts and procedural macros execute dependency code. The
checked-in `.cargo/config.toml` refuses ordinary Cargo builds and updates as an
accidental-use tripwire. Do not bypass it by clearing `RUSTC_WRAPPER` manually.

Use the repository's macOS Seatbelt wrapper, which has its own Cargo home and
target directory under `target/sandbox`:

```bash
make sandbox-check
make sandbox-test
make sandbox-build
./tools/sandbox-cargo <cargo command> [arguments...]
```

Use `make run` in place of `cargo run --release`. On macOS it builds under
Seatbelt, packages and ad-hoc signs the app with its App Sandbox entitlements,
launches a fresh instance, and waits for it to exit. On Linux the checked-in
`tools/run-linux` launcher intentionally performs an ordinary locked Cargo run;
there is no repository-provided Linux sandbox yet. Agents still must not launch
the app; the user runs and visually tests it. See `docs/build-security.md` for
the boundary and the separate fetch/update commands.

## Workflow

- Don't run the app — the user prefers to run and test it themselves
- Don't fight the system — avoid hacks/workarounds that go against how frameworks or platforms are designed; push back early when something seems like it's not meant to work that way
- Keep unrelated changes in separate commits whenever possible; avoid bundling housekeeping with feature work
- Only commit when explicitly asked
- When a design pattern or lesson emerges during work, propose additions to this document so future sessions start with that knowledge

## Git Commits

zsh heredocs fail in the sandbox because zsh writes temp files to `$TMPPREFIX` (defaults to `/tmp/zsh`), which is outside the sandbox allowlist. Fix by exporting it before the commit:

```bash
export TMPPREFIX=/tmp/claude/zsh && git commit -m "$(cat <<'EOF'
Commit message here
EOF
)"
```

## Puri Rules

- Widgets are pure functions (persistent widget state, props) → (draw calls, handlers). Puri holds nothing between frames, mints no identity, retains no hierarchy.
- Hover mirrors painting: `puri::hover::Claim` either names a target or occludes (the claim analog of an opaque fill), asked topmost-first over settled geometry; hover itself is derived per pass, with `LazyPointer` as the input-side dead-zone filter. Never store a resolved hover as an input to building a frame.
- Activation and picking lower into the same front-to-back pointer handler chain as raw input; never dispatch these as separate phases. The shell supplies the settled hover and its owning view explicitly at dispatch. Occlusion blocks pointer starts, while motion and release for active gestures remain available beneath it.
- Event acceptance controls propagation; gesture startup is an explicit update to caller-owned state. Compose selection and drag startup in the same accepted interaction rather than inferring a gesture from an unrelated handler returning true.
- Projection gesture continuations have one caller-owned active slot. The accepting handler installs the continuation; it owns motion until release or cancellation. Keep domain updates and undo grouping in the continuation, outside platform dispatch. End it when replacing or restoring the document and at a save boundary.
- Batch continuous pointer input before rebuilding a frame, including active drags. Preserve observed samples in order; handlers may use only the latest or integrate the full path. Release/cancellation must flush pending motion first. Do not introduce a per-widget batching flag or discard earlier samples in the shell.
- Durable widget helper state contains only caller-owned content and cross-frame interaction data. Font, paint, affixes, focus, placeholder, and similar presentation inputs belong to the current description and are captured by its transient handlers.
- Platform services are caller-supplied capabilities materialized in dispatch context; Puri must not construct global clipboard, clock, or window services itself.
- Focus is an input: the app owns who has focus and tab order; helpers are pure and advisory. The focused text widget emits an IME caret rect as output.
- No hidden framework caches. The only approved cross-frame computation memo is caller-threaded text shaping. Each visible canvas program records once per frame, sharing that recording between hit-testing and painting. Every changed frame input remints and presents a whole frame; never add event-specific relevance tests or partial invalidation. If that becomes too slow, build one general dependency-tracked invalidation system, including observations of missing definitions and ordered definition sets. The event-to-redraw pending frame and within-frame layout DAG sharing are pipeline staging and algebra, not caches.
- Puri is layout-neutral: it owns the `Placement` geometry contract, while the consumer owns measurement composition, layout nodes, containers, and traversal. Puri text and editor descriptions expose metrics and accept a settled placement; interaction helpers register against one. Do not make a particular layout algebra part of a Puri widget's type.
- Progred's layout is the baseline box algebra plus ordered layout alternatives (Wadler-flavored: first natural form that fits wins, the last accommodates); no general layout engine. Keep measurement and placement separate. Use `around` when a Progred wrapper must control whether or when its subtree places; derive ordinary leading work with `before` rather than adding special cases. The box interpreter lives in `progred::display` and invokes opaque widget/preparation functions; do not add document traversal or control variants to Layout. Native widgets and the editor share `HoverPass` as placement output (`Placed` is an alias). Call it to resolve hover and produce a `Fragment` (`Ready`) containing independent paint and event continuations plus navigation. Do not retain a probe catalogue for the editor to interpret, and do not require painting to obtain a handler.
- Keep layout honest about painted geometry: derive anchors and clearance from the same metrics, outlines, and stroke widths used for drawing. Intentional padding and gaps are explicit styling inputs; do not tune separate offsets to compensate for borders or other geometry owned elsewhere.
- Every placement callback receives an explicit `Placement`: the widget's `rect`, the container's `available_rect` offered for optional expansion, and the effective enclosing `clip_rect` (the intersection of ancestor axis-aligned layout clips, not pre-intersected with the widget). Ordinary children inherit the clip unchanged; an actual clipping container intersects its bounds into it. Available space is not a clip or a hit target: an explicit placement combinator may adopt it, without changing intrinsic measurement or rerunning alternatives. Never thread clipping as mutable context. Hover and gesture starts must be inside both rects; motion and release for an active gesture stay unbounded. Canvas clips remain a separate, arbitrary-shape drawing concern.
- Masonry is a quarry, not a foundation: vendor high-value files (text input first) with attribution and purify in place; rewrite trivial widgets; never inherit its tree, pods, or ctx protocol.
- Keep the Puri runtime separate from widget catalogs. Reusable composed widgets belong in the sibling `puri-widgets` package and remain pure consumers of Puri; Progred owns document adaptation, layout, and popup policy.
- Progred-owned widgets may work directly with the editor. Borrow current inputs while building; capture props and locations in transient handlers, then pass `&mut Editor` at dispatch and call ordinary helpers. Do not introduce callback dictionaries merely to keep these widgets generic over an opaque world or in an artificial separate crate. Puri itself stays editor-independent.
- Extend Puri only as Progred needs it.
- Native widget preparation requests document-site state only when needed; inert decorators must not construct editing state or capabilities. Defer drawing at widget granularity, then call the canvas directly after hover settles. Do not implement the placement output as a Canvas that allocates a closure for every drawing operation. Hover claims and visual feedback are independent, explicitly composed decorators.

## Key Design Rules

- Prefer simple constructs and reusable combinators that build layers of abstraction. A composition should remain an ordinary input to further composition: partial projections combine into a partial projection, completion providers into a provider. Build higher-level behavior through these interfaces rather than adding domain-specific cases to central machinery. Lowering may optimize the representation and execution of those layers, but must preserve their meaning and observable behavior. See [MOTIVATION.md](MOTIVATION.md#simple-constructs-and-combinators).
- GID is the native logical model and future binary storage stack, not a textual format. Documents are structural values plus a direct `CellId -> Value` table; an absent entry is a bare cell. `name`, text, and Grap's tagged absence values are libraries embedded above the data layer, never GID features. The binder notation and the checked-in `*.gid` fixtures are a temporary text bridge only; when a native binary representation lands, it takes over the `.gid` extension and the bridge moves aside.
- The GID core has only two atoms: cell references and blobs. Record labels are always cell identities. UTF-8 text is the open `libraries::text` record convention over a blob, not a primitive; a line projection recognizes the text or f64 facet even when the record has other fields.
- Resilient to invalid GID states — projections specify the happy path but must fall through gracefully to default/raw rendering; never crash or hide data on unexpected values
- Controls supply sensible defaults for absent selection payload fields. Selecting a writable missing location enters its ordinary picker without requiring an explicit pending marker; projection is read-only and input materializes query state when needed. Missing-name markers only select the location; the name library owns text completion there. Keep explicit query modes available for intentional requests, not as prerequisite setup for every caller.
- Normal display is one explicit projection composed from ordered partial projections above one total structural fallback. Pass that projection explicitly through recursion; do not bury it in display context. Each partial is a function that checks its preconditions and fails closed. A partial returns a `progred::display::Layout<Editor, Hovered>`: boxes, paint-parametric Puri leaf programs, generic hover claims, and owned callbacks receiving `&mut Editor` at dispatch. A Puri leaf contains only shaped-at-lowering text or fill/stroke/clip canvas operations; it must never acquire document locations, selection payloads, editing rules, labels, queries, or event policy. There is no parallel Progred drawing language and no central action enum or reducer. `Layout` is a reusable program over the object-safe builder interface, not an enum. The production builder prepares one choice graph; after alternative selection that graph invokes placement callbacks directly. `Measured` is only an extent plus a one-shot placement function, never a second container tree. Structural recording is a separate test interpreter. Callbacks become Puri handlers. Libraries offer those functions; `stack::load` retains their ordered definition maps and composes one reusable `Projection` above the structural fallback. Raw is that fallback alone — the same `Layout` language, total rather than `Option`. `descend` is a preparation function using an explicitly supplied projection scope: it receives one GID `Step`, extends stored provenance, and resolves that location. `at` and `transient` use the same function boundary, not layout opcodes. `Follow` carries the stable resolution source (`Document` or a library identity), never an ordinal into the currently loaded stack. `at` and `descend` accept independent optional replacements for the current projection and the descendant default; supplied functions replace rather than implicitly compose. `ProjectionInput.default_projection` exposes one composed partial. Local helpers explicitly compose a custom partial before that default only at the target; scoped helpers pass the composition both here and below. Container combinators pass local child projections one step at a time: lists accept an optional element partial, records a field-to-optional-partial function, and standard containers use those same renderers without overrides. Partials receive `Option<&Value>`: `None` denotes a missing location, never a fabricated GID value. A failed `descend` lookup still tries the chosen partial at that real location; if it declines, the fallback renders the ordinary empty picker. There is no separate missing-layout parameter. Starting the same projection at a transient root handles computed values; source provenance, not a separate derived operation, controls editability and selection attribution. A later, more specific partial can wrap an earlier facet (for example a unit around f64).
- Documents currently contribute no library cells, foreign functions, or projections. Do not discover configuration through fixed-address cells or other data outside ordinary root reachability. A future document-local library mechanism needs an explicit design whose configuration and definitions are reachable from root.
- Pane entries are ordinary values in the document's root-reachable side lists. Opening, moving, and deleting panes edit those lists and participate in document history. Presentation wrappers belong to the presentation library, not workspace layout. The normal document projection leaves `{value, projection}` declarations editable; pane views try the presentation library's declaration interpreter only at entry, including through cell definitions. Nested values, computed results, and the source shown after an absent result use the normal projection. Pane entry following is separate from explicit local or scoped projection composition.
- Completion is an ordinary native widget function placed by the projection that renders the pending field or value; its explicit kind/provider arguments go to a scoped app adapter returning the shared measured widget output. Never hide a provider in traversal context. The control supplies an optional lazy vocabulary and whether it is completing a field or value. Active providers receive one contextual request: query, field/value kind, suggestion/Everything scope, source-qualified path, and read-only path lookup. The path names the missing value or the record receiving a label. A local provider takes precedence; otherwise library providers compose in library order. None leaves the vocabulary unspecified; Some(empty) specifies an empty narrow list. Progred adapts GID values and editor actions, owns floater policy and selection state, and lowers the reusable pure `puri-widgets` completion rows through the existing column and scroll container; do not implement a second scroll viewport inside the widget. Invoke vocabulary providers only for the active picker, not for inactive empties. When a provider is present, its offers are the default list; a trailing `…` affordance adds universal atoms, constructors, and cell search, then disappears for the lifetime of that picker. Changing the query filters the expanded list without collapsing it. With no specified vocabulary, show the universal list directly. Root templates, root fields, and domain-specific suggestions use this same request; keep applicability decisions in libraries, not root-specific host hooks. Label offers omit fields already present. A completion may supply an `on_commit` native continuation over staged site/selection state; `site::grap` adapts Grap callables to that same interface. Stage the continuation together with the insertion. The continuation may open a pending child without inserting a placeholder value. Retain the exact visible offers in the placed frame so hover and commit never reconstruct a different list.
- Text and number partials call the stock native line-widget function, supplying spelling, affixes, and a conversion callback owned by the current handler. Native controls use native callbacks; the line library adapts Grap conversions explicitly. Persistent selection never owns conversion wiring. The caller runs each Puri editing operation, then converts changed text and records undo at that boundary; there is no shell-wide post-event write-through. `Layout::widget` carries its opaque measurement/placement continuation; there is no line-editor constructor or interpreter arm in layout. The editor supplies current state and scoped editing capabilities, and incorporates the widget's native render closures, handlers, hover claims, and navigation transition. The shared `CanvasSink` primitive interface draws directly into the chosen backend without GID encoding; `Canvas` supplies its generic convenience methods. The earlier Grap implementation proved that Grap controls can use shaped geometry, generic events, and scoped site/selection capabilities, but duplicating Puri's editor composition there had reached diminishing returns. Generic Grap handlers receive GID events and caller-supplied capabilities. `site path` exposes the projected location through the path library; `selection get` reads the local payload, and `selection set` takes an explicit encoded path and payload in the current document/view context. Selection changes are effectful calls, never a special handler return format. Capability writes commit unless the handler explicitly declines or evaluation halts. An ordinary absent result keeps its effects, including a successful clear. Tests may replace the foreign-call interpreter. Focus, editor text, caret, IME, and drag remain Rust-owned `LineEditState` beside the selection payload. Derive their GID description on demand and decode capability replacements once; do not retain and synchronize a second editor-state copy.
- Compile-time code generation must fail loudly — if the semantics-driven codegen returns, malformed GID data must produce a clear compile error, never be silently skipped
- Grap syntax is ordinary `Value` structure interpreted through library cell IDs. The semantic runtime owns only lambda/application, GID-valued closures and foreign-callable tags, stable evaluator absent identities, and evaluation mechanics. Its Rust implementation may carry equivalent host representations while evaluating: records and lists constructed by control functions keep lowered children, and the evaluator privileges the f64 convention directly so native numbers stay unboxed through calls, containers, and environments until a generic boundary asks for `Value`. An original source `Value` is retained so metadata survives unchanged pass-through. Privileged knowledge of a library convention is an accelerator only, never a capability: each such library must remain expressible externally, evaluating correctly at reduced speed, and to Grap it reads as an ordinary library. These are implementation optimizations, not Grap syntax or GID primitives; the f64 library still owns its functions, projections, and absences, and re-exports the convention the evaluator holds. The built-in `libraries::grap` module owns its self-description, `evaluate` Rust function, and projection. Geometry and CAD concepts remain separate Progred libraries.
- The structural fallback projects cells deeply. Grap expression and callable positions request a shallow named-cell projection at direct use sites. Compound forms explicitly choose their children. Lambda parameters use the shared list combinator with a declaration partial; match cases, let/where bindings, and do expressions supply their own element partials. Patterns explicitly scope the binder partial over their subtree, reusing ordinary container recursion and atom facets. Inert data, declaration metadata, and quoted templates otherwise use the normal deep fallback; local use-site overrides do not leak into them. Call arguments follow a stored or inline lambda's declared parameter order, then show extra fields in the ordinary named/unnamed order; inspecting that order is a raw cell-definition lookup, never evaluation, so computed callables and FFIs use the fallback. `at` preserves the child's stored path while selecting current and descendant projection functions; use explicit composition instead of teaching the raw structural fallback about Grap.
- Put more specific domain projections before general ones. The control library projects coherent `match` calls as ordered `pattern → expression` cases and projects `{bind: cell}` distinctly; the arrow targets its expression like a field head targets its value. Malformed shapes decline whole so the general Grap-call or structural projection still exposes every value.
- Grap evaluation is explicit in projections: `evaluate` is a value partial the built-in Grap library offers, not a field hook in the structural walk and not evaluator syntax. A record with an `evaluate` field is shown as the stored expression (nested under that field, so its path stays `…+Key(evaluate)`), then `→`, then the returned `Value` projected from a transient, read-only root. If that result itself has an `evaluate` field, the same partial matches and evaluates it, continuing the same fuel allowance. Recognition is open, like text and f64: other fields do not block it, and an earlier partial in the editor's list wins if more than one matches. The `→` is a dim leaf in a `group`; Raw shows only the stored record. The evaluator does not observe the field; a host that never loads the projection never sees it. Calls and lambdas elsewhere remain editable GID data; a returned call-shaped value is not evaluated again. The separate `grap` field is ordinary library vocabulary saying its contents belong to the Grap domain; it requests no evaluation and currently has no editor behavior.
- Grap lambdas currently carry an ordered list of explicit parameter cells; calls put arguments directly under those cell labels. This is a concrete bootstrap shape, not a settled pattern language. Evaluating an untagged `{params, body}` lambda produces `{closure: {params, body, environment}}`. Grap-defined calls are strict: every declared argument field is evaluated before the body runs, and their lexical environment is an ordinary GID record inside that closure value. Effects are explicit foreign calls and scoped capabilities, as in event handlers. Unrecognized records and lists are inert data and are never recursively searched for expressions.
- GID conventions identify records by required positive evidence and are open to unrelated fields unless a domain explicitly defines a closed shape. Facet projections (text, f64) use that same open recognition so a wrapper can defer to them.
- In the normal projection, display named record fields first in alphabetical display-name order (CellId breaks equal-name ties), followed by unnamed fields in CellId order. Raw has no names, so it remains CellId-ordered.
- Cells resolve lexical binding first, then ask `Host::resolve` for one definition: the document definition, otherwise the first loaded library definition. No definition yields missing-cell absent. Duplicate definitions across sources are tolerated but are not a composition or overloading mechanism. Normal names and structural display use the selected definition too; duplicate indicators and inspection UI are deferred. A native definition pairs a descriptive Value with its Rust implementation: ordinary evaluation uses the description without invoking native code. Thus a named FFI evaluates to its ordinary name record. Scoped capabilities are consulted only for calls and call preparation. Direct Rust and Grap calls share `{function: cell, ...arguments}` syntax; the existing inert `{ffi: cell}` reference carries a callable through an evaluated argument without reading that cell's data. A stored `Follow` path names the document or a stable library identity, so loading or reordering libraries cannot silently retarget editor state.
- Rust function implementations receive the call record, the calling `Environment` (bindings), and the live evaluation `Context` (fuel and the rest). They look up the fields they consume as raw argument expressions. They may inspect, return, forward, or recursively evaluate those expressions through the context in that environment or an explicitly derived one; ordinary strict Rust functions evaluate all of theirs. The environment becomes a GID record only when Rust explicitly hands it to Grap. Semantic failure remains an ordinary absent `Value`; the host `Result` only propagates evaluator halting such as exhausted fuel. A Progred `Library` owns one sorted definition table and one partial projection. Libraries compose their own forms with `compose_partials` (first success wins; empty declines); the editor composes the resulting functions in library order above its total structural fallback. Each entry is an ordinary Value or a shared native definition holding its descriptive Value and Rust implementation. Built-in builders join data and function declarations once during construction; they are not separate lookup registries. The library's description (currently its name record) is an ordinary definition under its library CellId. A repeated definition replaces the prior entry. Loaded libraries are an insertion-ordered unique map keyed externally by stable random library CellIds; the identity is not a field inside the library, and loaded libraries are read-only. Repeating a library identity replaces its complete contribution in place before projections and completions are composed. Direct Grap calls use the same definition lookup as reads: a native definition invokes its Rust implementation, while an ordinary value is evaluated as the callable. Every result is definitive, including explicit decline; non-callable values return absent without trying another source. Scoped capability functions still override this lookup. Effects stay in caller-owned evaluation-local data. Rust capabilities wrap observable writes in `Context::effect(|| operation)`, including drawing, selection/annotations, and deterministic random advancement. Evaluate arguments and check applicability before entering the effect body; the combinator marks the effect and returns the operation's result without snapshots. Each call compares the effect counter with its entry value, so strict arguments and nested calls count too. Explicit decline after an effect halts with a tagged absent and prints an error; it never falls through. Ordinary absents remain definitive values, including successful clears. There are no per-call snapshots or rollback. The host stages and may discard the complete editor operation or drawing recording. Fuel is never restored. Keep effect interpretations pure overall: update temporary local data, not external systems. `stack::load` retains library boundaries; projection functions compose explicitly in library order above the structural fallback, never by registering a shared projection CellId. The current host partials are Rust callbacks; ordinary Grap callables can already serve presentation declarations. Conceptual Progred libraries are modules in `progred::libraries`, alongside their editor-facing widgets; editor-authored libraries can later lower into the same representation without supplying Rust FFIs. Loading is an explicit editor operation, not an FFI or reserved-cell discovery. Every absence is an explicit open `{absent: reason-cell}` value. The stable reason cell owns its names and other static metadata; code tests the CellId payload, never human-readable text.
- Grap evaluation always produces a `Value`; missing cells, malformed syntax, cycles, and exhausted fuel are tagged absence values with stable reason cells. Occurrence-specific details (missing cell, offending value, cycle) belong in that open absent record. There is no parallel Rust diagnostic channel. `Evaluation.completed` distinguishes an actual evaluator halt from a normally returned value, even if that value has the same absent reason.
- Evaluation itself has no quote/literal form. Raw Rust handlers already receive inert expressions, and a handler returning one returns data because function results are not evaluated again. The control library's ordinary Rust `quote` function walks its raw expression and replaces original `{unquote: expression}` leaves by evaluating their expressions in the quote caller's environment; it never revisits spliced results. Unquote-shaped records outside that traversal are ordinary data, and other ordinary data remains self-evaluating without quote. `evaluate` is likewise a registered function, not evaluator syntax.
- Grap's control library `match` evaluates one explicit subject once, tries ordered structural cases, and evaluates only the first matching expression in the calling environment extended with its bindings. Keep the subject local to that operation; do not introduce an implicit match-value binding. Record patterns are open, list patterns are exact and ordered, `{bind: cell}` captures, and repeated binders require equal captures. A final binder is the ordinary catch-all; no matching case returns absent. An absent result from a selected expression is still the result, not fallthrough.
- Absence composition belongs only to explicit ordered-choice operations, not to cell lookup or an ambient evaluator trace. An entirely unmatched `match` returns ordinary mismatch absents, combining several as `{absent: no-alternative, causes: [...]}`; it does not implicitly decline an enclosing function. A handler can supply an explicit declining catch-all case. A selected match expression is definitive even when absent, and evaluator halts propagate immediately. Do not accumulate an ambient failure trace.
- Well-known library cell IDs are once-minted random identities, never names or hashes of names; readable names are ordinary `libraries::name` GID facts. Mint fixed identities from 16 unmodified OS-CSPRNG bytes (`new_cell_id`/`getrandom`, or `openssl rand -hex 16` when producing a source literal), never from a UUID generator.
- `CellId` is an opaque 128-bit identity, not an RFC UUID: all bits are random, with no version or variant fields. Preserve the text bridge's canonical 32-hex spelling and the existing hyphenated Serde spelling.
- Until text-bridge documents exist outside this repository, change its parser and checked-in `*.gid` fixtures in lockstep. Do not add versions, migration branches, or compatibility readers.
- Evaluation is fueled. An `evaluate` wrapper projects absent values like every other transient result; Raw always exposes its stored expression.

## Testing

- Test pure logic directly; don't write UI tests that just verify strings pass through to draw calls
- Pure `render`/`update` functions mean snapshot/property tests on draw-list data need no windowing harness — prefer them; use vello headless readback only when a visual golden is genuinely needed
- Visual changes are checkable without launching the app: `./tools/sandbox-cargo test -p progred svg_bench` renders the sample and focused Grap demo through the real projection to `target/raw_projection.svg` and `target/grap_demo.svg`, and `./tools/sandbox-cargo run -p puri --example delimiter_bench` renders the drawn-delimiter family against the font's own outlines; view any of them with `qlmanage -t -s 1600 -o <dir> <svg>`

## Code Style

- Very limited comments — code should be self-documenting
- Expression-oriented where possible
- Prefer long expressions broken across multiple lines over multiple statements with intermediate names — naming is hard, avoid unnecessary names
- Exception: extract helper functions when intermediate steps represent distinct semantic concepts — top-level function becomes a readable composition of named transformations (functional decomposition)
- Prefer free functions with explicit parameters over methods when `self` isn't needed — makes inputs/outputs clear, easier to unit test, enables composition in a single method that has access to `self` (Haskell-style)
- Look for generic abstractions — extract patterns in how computations combine and data flows (the way `fold`/`map`/monads abstract over structure, not specific operations)
- Dispatch on node type via `try_wrap`, not edge presence — checking for a marker edge to mean "is a sum" is duck typing that breaks if an unrelated node shares that edge label
- Apply Haskell-style thinking (explicit data flow, pure function composition) but idiomatic Rust syntax — don't fight the language
- Factor out common assignments: `x = if cond { a } else { b }` not `if cond { x = a } else { x = b }`
- Functional style: iterator chains, `try_fold`, `filter_map`, `std::array::from_fn` over mutable accumulators and loops where it doesn't make things worse
- Avoid `let mut` when a functional alternative is equally clear
- No `isX()` predicate methods — use `matches!` or pattern matching at the call site
- Eliminate partial functions: use `split_first`/`split_last` over manual indexing
- Return references for non-trivial types (let caller decide to clone); methods on small structs enable disjoint borrow checking over methods on the parent
- Avoid early returns — prefer `if let`, `match`, or expression-oriented alternatives over `let-else return` / `return` in closures
- Dead code should be deleted, not commented out
- Events describe what happened (user actions), not what to do about it; interpret them in one place after rendering
- Push back if something seems wrong
